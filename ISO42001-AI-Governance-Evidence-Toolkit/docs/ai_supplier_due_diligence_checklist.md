# AI Supplier Due Diligence Checklist

> Template for SME AI governance discussions. This is not legal advice and should be adapted to the organisation's procurement, security, privacy and contractual requirements.

## Purpose

This checklist helps an organisation review AI tools and model providers before adoption or expansion. It is designed for practical AI governance readiness work, including ISO/IEC 42001-style management-system thinking, cybersecurity GRC and EU AI Act readiness conversations.

## Data handling

| Question | Expected evidence |
|---|---|
| What categories of data will be entered into the tool? | Data category notes |
| Is personal data processed? | Privacy review note |
| Is confidential business information processed? | Business owner approval |
| Is sensitive data excluded or minimised? | Data minimisation procedure |
| Is customer data used to train supplier models by default? | Supplier documentation or contract terms |
| Can the organisation opt out of training or data reuse? | Supplier setting or written confirmation |
| Is data retained by the supplier? | Retention policy reference |
| Can data be deleted or exported? | Deletion/export documentation |

## Security and access control

| Question | Expected evidence |
|---|---|
| Does the supplier support SSO or enterprise identity controls? | Security documentation |
| Can access be limited by role? | Access-control screenshot or policy |
| Are admin roles separated from ordinary users? | Role matrix |
| Does the tool support audit logs? | Audit-log documentation |
| Is multi-factor authentication supported or required? | Security setting evidence |
| Are integrations reviewed before connection? | Integration approval record |

## Compliance and assurance

| Question | Expected evidence |
|---|---|
| Does the supplier provide security certifications or assurance reports? | SOC 2 / ISO / equivalent documentation if available |
| Is there a DPA or privacy addendum where needed? | Contract or DPA reference |
| Are processing locations documented? | Supplier documentation |
| Are subprocessors listed? | Subprocessor list |
| Are material changes communicated? | Contract or notification terms |
| Is there an incident notification process? | Supplier incident terms |

## AI governance considerations

| Question | Expected evidence |
|---|---|
| What AI capability is being used? | Use-case register entry |
| Is the output used for decisions, drafting, analysis, or automation? | Process description |
| Is human review required before use? | Human oversight requirement |
| Are limitations and failure modes documented? | Impact assessment note |
| Are users trained on safe and acceptable use? | Training record or awareness material |
| Is there an escalation path for harmful, biased or inaccurate outputs? | Incident/complaint handling process |

## Risk rating

| Rating | Meaning | Suggested action |
|---|---|---|
| Low | Public or low-impact use with human review | Approve with basic policy controls |
| Medium | Customer-facing, operational or internal decision-support use | Require owner, review process and evidence trail |
| High | People-impacting, regulated, sensitive or security-relevant workflow | Require formal review before deployment or expansion |

## Notes

Supplier review should be repeated when the tool, use case, data category, integration model, contractual terms or supplier security posture materially changes.
