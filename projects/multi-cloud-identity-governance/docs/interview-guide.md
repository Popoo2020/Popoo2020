# Interview demonstration

## Two-minute explanation

“I built a local identity-governance simulator for a fictional distributor using Entra, AWS and Google Cloud. The main case is an operations employee moving into finance. Adding finance access is only half the problem: old permissions must be removed, incompatible combinations prevented, and the decision traceable.

“The engine derives a plan from workforce facts and a role catalog. New grants require manager and resource-owner approvals tied to that plan. It removes obsolete assignments first. If a removal fails, it freezes new grants and reports the unresolved state instead of presenting the move as successful.

“I included successful and failure cases, strict import boundaries, reconciliation and evidence bundles. Everything demonstrated is local and synthetic. The project does not authenticate real approvers or modify a cloud tenant. The next integration step would be an authenticated, read-only collector in an isolated environment, followed by separately controlled execution.”

## Five-minute hands-on route

From `projects/multi-cloud-identity-governance` in the portfolio checkout, using the Python environment described in the [project README](../README.md):

```bash
python -m identity_governance demo --output build/demo
```

The output directory must be empty. For another run, choose a fresh `--output` path and adjust the paths below; keep earlier evidence intact.

| Time | Show | Explain |
|---|---|---|
| 0:00–0:45 | `examples/scenario.json` | Four synthetic identities, named owners, three business roles and two explicit conflicts. |
| 0:45–2:00 | `build/demo/mover/report.md`, then `plan.json` | Shared staff access remains; three removals precede three grants. Point to the intended finance role. |
| 2:00–3:00 | `build/demo/mover/approvals.json` and `result.json` | Approvals bind to a plan and operation; reconciliation reports the bounded assignment result. |
| 3:00–4:00 | `build/demo/failed-removal/report.md` | An injected failure preserves the unresolved old assignment and blocks new grants. No provider call was attempted. |
| 4:00–5:00 | `audit.jsonl`, `manifest.json`, and verification | Show traceability and explain what hashing cannot prove. |

```bash
python -m identity_governance verify --bundle build/demo/mover
python -m identity_governance verify --bundle build/demo/failed-removal
```

The failure bundle can pass an integrity check while documenting an unsuccessful transition. Integrity and operational success answer different questions. For additional discussion, open the `unapproved`, `leaver`, `contractor-expiry` or `access-review` report generated by the same demo.

## Questions worth answering precisely

- **Is this deployed?** No. It demonstrates executable local decisions and evidence, plus a documented deployment design.
- **Are the approvals secure?** The engine checks binding, ownership rules and validity. The identities are synthetic assertions; a production approval service must authenticate them.
- **Does removal terminate every session?** No. Provider propagation, existing tokens and alternative access paths need separate verification.
- **Can it import everything?** No. Thin normalizers intentionally reject unsupported forms rather than guess effective access.
- **Is the evidence tamperproof?** No. Hashes expose inconsistency, but someone controlling the whole bundle can recompute it.
- **Why no AI decision core?** Access decisions need explicit, reproducible policy. More policy checks can be added without making authorization probabilistic.
